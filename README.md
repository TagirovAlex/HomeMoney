## 🚀 Обзор Проекта (Project Goal)
Сервис представляет собой веб-приложение для локального учета личных финансов. Его ключевая особенность — предоставление гибкого и безопасного инструментария с возможностью фиксации транзакций через два канала: полноценный, функционально богатый **Веб-интерфейс** и минималистичный, высокодоступный **Telegram Bot**.

## 🏗️ Общие Архитектурные Требования (Architecture & Principles)
*(Блок требований к методологии разработки)*

### Технологический Стек (Tech Stack)
*   **Язык:** Python 3.10+
*   **Веб-фреймворк:** Flask или FastAPI (предпочтительнее для микросервисного подхода).
*   **Мессенджер API:** `aiogram` версии 3.x (Обязательно асинхронная работа: `async`/`await`).
*   **База данных:** PostgreSQL (или SQLite, с возможностью миграции на Postgres).
*   **ORM/DB Access:** SQLAlchemy (для реализации паттерна Repository).

### Принципы Разработки (Best Practices)
1.  **Изоляция Сущностей (Isolation):** Код должен быть строго разделен по слоям: `Data Layer` (репозитории), `Business Logic Layer` (сервисы, использующие паттерн Service Use Case), и `Presentation Layer` (Web Routes / Bot Handlers).
2.  **Безопасность:** Обязательное использование хеширования паролей (`Bcrypt`). Все точки входа должны проходить строгую валидацию данных.
3.  **Архитектурный паттерн:** Применение **Repository Pattern** для полного отделения кода от деталей доступа к данным (DB).
4.  **Производительность Бота:** Вся работа с Telegram Bot должна быть реализована асинхронно (`asyncio`) для обеспечения высокой отзывчивости.

### Требования к Развертыванию и UI/UX
*   **Среда:** Debian 12 (Bookworm) или новее.
*   **Зависимости:** Минимальный набор сторонних зависимостей Python. Никаких дополнительных контейнеров (`Docker`).
*   **Мобильность:** Интерфейс обязан быть **Mobile-First** и полностью адаптирован для использования на всех типах мобильных устройств (Responsive Design).
*   **Дизайн:** Должна реализоваться функция переключения между двумя темами: **Светлая Тема** и **Темная Тема**.

## ⚙️ Функциональные Модули (Functional Modules)

### [МОДУЛЬ I] Система Пользователей и Безопасность
*   **Ролевая Модель:** Реализация ролей `Администратор` (полный доступ, настройки) и `Пользователь` (только личные данные).
*   **Авторизация:** Стандартная система логина/пароля.

### [МОДУЛЬ II] Управление Финансовыми Активами (Accounts & Assets)
Система должна поддерживать учет не просто баланса, а нескольких отдельных, управляемых активов:
1.  ✅ **Cash / Наличные:** Счет для физических денег.
2.  ✅ **Checking Account / Основной Счет:** Банковский счет/карта.
3.  ✅ **Savings Account / Депозит:** Учет сбережений (с отдельным балансом).
4.  ✅ **Investment Portfolio:** Учет инвестиционных активов (требует учета *стоимости* актива, а не только наличного остатка).
5.  **Начальный Остаток:** Возможность привязать и указать начальный баланс для каждого нового счета.

### [МОДУЛЬ III] Транзакции (Core Transaction Logic)
Все операции должны проходить через **Service Layer** и привязываться к конкретному Счету.

| Тип Операции | Назначение | Обязательные поля |
| :--- | :--- | :--- |
| 💸 **Расход (Expense)** | Отток средств на повседневные нужды. | Сумма, Дата, Категория Расхода, Связанный Счет, Описание. |
| 💵 **Доход (Income)** | Поступление средств. | Сумма, Дата, Категория Дохода, Источник/Счет-получатель. |
| 🔄 **Перевод (Transfer)** | Движение между своими счетами (A $\to$ B). | Сумма, Дата, Счет-источник, Счет-получатель. *(Не влияет на общий финансовый баланс).* |

### [МОДУЛЬ IV] Управление Расписанием
*   **Категоризация:** Админ должен иметь возможность создавать/редактировать иерархические категории (расход/доход).
*   **Бюджетирование:** Возможность установки ежемесячного лимита расходов по каждой отдельной категории. Система должна визуально отслеживать остаток бюджета.
*   **Регулярные Платежи:** Модуль для регистрации обязательных, повторяющихся платежей (ежемесячно, ежеквартально).

## 🤖 Telegram Bot Интеграция (P2)
*(Блок функционала бота)*

### [МОДУЛЬ V] Ботовая Обработка Транзакций (Telegram Handler)
*   **Технология:** Использование `aiogram` v3.
*   **Конфигурация Админа:** Администратор обязан привязать список пользователей к боту через специальный интерфейс, связывая `Telegram User ID` с системным аккаунтом пользователя.
*   **Интерфейс Пользователя (UX):** При первом входе `/start`, пользователь получает главное инлайн-меню: [💵 Доход], [💸 Расход].
*   **Процесс Ввода (State Machine):** Бот должен вести диалог, минимизируя ввод текста.
    1.  Пользователь выбирает **Тип Движения** (Расход/Доход).
    2.  Бот запрашивает выбор **Категории** через инлайн-меню.
    3.  Бот запрашивает выбор **Счета** (если необходимо).
    4.  Бот запрашивает **Сумму**.
    5.  После получения всех данных, Bot Handler передает запрос в `FinancialService` для фиксации транзакции.

## 📊 Отчетность и Бэкапы
### [МОДУЛЬ VI] Дашборд и Аналитика
*   **Dashboard:** Общий баланс (суммарный остаток всех счетов). Визуализация потоков средств за выбранный период (Income vs Expense graph).
*   **Отчеты по категориям:** Диаграммы распределения расходов/доходов.
*   **Управление БД:** Админ-панель должна содержать механизм **ручного бэкапа** всей базы данных в легковосстановимый архив (`.sqlite` или `.dump`).
